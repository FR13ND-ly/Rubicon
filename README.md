# Rubicon

Rubicon is a bachelor's thesis project exploring a Rust-hosted server-side rendering framework for Angular. The proposed architecture uses Rust for HTTP handling and application services, with an embedded JavaScript runtime for Angular rendering.

The repository contains documentation drafts, an Axum HTTP server connected to a persistent JavaScript rendering worker, and an Angular SSR reference application. The Rust executable now loads the application's neutral build and serves Home and About HTML rendered by Angular in embedded V8. Browser asset delivery and hydration through Rust, lifecycle guarantees, and performance evaluation remain future work.

The [Angular reference application](examples/angular-demo/README.md) pins all direct Angular packages to 22.2.2 and contains Home and About routes, shared navigation, and a signal-based counter. The initial welcome application's production build and asset delivery were verified. For the routed Node.js reference, the development build, two existing root-component tests, direct SSR access to both pages, browser hydration, counter interaction, and navigation checks passed. It uses explicit `RenderMode.Server` routes and accepts the local hostnames `localhost` and `127.0.0.1`. The [Rust HTTP follow-up](docs/experiments/004-angular-http-adapter.md#repository-verification) now verifies the same pages through Rubicon's neutral adapter, including query routing and HEAD. It provides no benchmark results or browser hydration evidence through Rust.

The Rust package is defined in [crates/rubicon/Cargo.toml](crates/rubicon/Cargo.toml), with Axum pinned to 0.8.9, deno_core to 0.412.0, deno_web to 0.290.0, deno_webidl to 0.259.0, deno_fetch to 0.283.0, deno_net to 0.251.0, Tokio to 1.53.2, and Serde to 1.0.229. The executable listens on `127.0.0.1:3000`; GET and HEAD requests invoke the render export built from [server.rubicon.ts](examples/angular-demo/src/server.rubicon.ts). The generated entry is examples/angular-demo/dist/rubicon/server/server.mjs and requires its neighboring generated files. Home and About return 200 HTML; an unhandled route becomes a 404 text response. GET delivers the representation and HEAD omits its body. Static browser files are not served yet.

The runtime registers pinned Deno extensions and uses [web.js](crates/rubicon/js/web.js) to expose URL/encoding APIs, four timer functions, DOMException, Event/EventTarget, AbortController/AbortSignal, ReadableStream/WritableStream/TransformStream, Headers/Request/Response, and an initialized performance object. Runtime tests verify selected URL and UTF-8 behavior. Six worker fixtures cover microtasks, timer cancellation, Unicode stream pipelines, abort propagation, selected Web request/response semantics, and performance marks, measures, and explicit entry cleanup. Create and use JavaScriptRuntime within an active Tokio runtime context; the worker and runtime tests use current-thread executors. The [Web foundation verification](docs/specs/architecture.md#url-and-utf8-runtime-verification), [timer verification](docs/specs/architecture.md#web-timers-verification), [streams/abort verification](docs/specs/architecture.md#streams-and-abort-verification), [Request/Response verification](docs/specs/architecture.md#web-request-and-response-verification), and [performance API verification](docs/specs/architecture.md#performance-api-verification) record the setup and checks. The [Angular HTTP milestone](docs/specs/architecture.md#angular-http-integration-verification) records actual repository rendering through Axum. The HTTP response remains buffered; public fetch, host request cancellation, and browser hydration through Rust remain pending.

First build the neutral application from examples/angular-demo, then run the local server from the repository root:

```text
npm.cmd run build -- --configuration development,rubicon
```

```text
cargo run --locked --manifest-path crates/rubicon/Cargo.toml
```

The library's `JavaScriptRuntime` owns one embedded runtime, evaluates synchronous scripts through `execute_i64`, loads a main module, and calls exports through `call_export<TArgument, TResult>`, using serializable arguments and owned deserializable results. The public [Renderer](crates/rubicon/src/renderer.rs) accepts an owned [RenderRequest](crates/rubicon/src/request.rs), containing `request_id: String`, `url: String`, `method: String`, and `headers: Vec<(String, String)>`, and sends it with each job to a dedicated thread that owns the runtime and loads the module once. The worker borrows the request, converts it directly to a V8 object through `serde_v8::to_v8`, and passes it to JavaScript. The worker selects `RenderResponse` as the result type and transports that owned value through the reply channel. Its fixed queue holds up to 16 waiting jobs, with one render active at a time. Cloning `Renderer` shares access to this worker.

The library exposes [RenderResponse](crates/rubicon/src/response.rs), containing `status: u16`, `headers: Vec<(String, String)>`, and `body: String`, with Serde deserialization support. The Angular adapter returns an object with these fields. The repository worker integration check uses controlled fixtures to verify statuses 302, 404, and 200, redirect Location, two separate Set-Cookie pairs, exact Unicode body text, and continued execution after JavaScript and result-conversion errors. See the [structured response verification](docs/specs/architecture.md#structured-response-transport-verification).

The public [into_http_response](crates/rubicon/src/http_response.rs) converts a `RenderResponse` into an Axum response and is called by the HTTP handler before delivery. It accepts final statuses 200 through 599, requires empty bodies for 204, 205, and 304, validates header syntax, preserves repeated fields with `append`, and rejects renderer-supplied transport headers such as Content-Length, Transfer-Encoding, and Connection. It does not insert a default content type. Four library tests verify redirect metadata, repeated cookies, exact UTF-8 body bytes, and rejection cases. Invalid response metadata produces a generic HTTP 500, with details and request identifier logged server-side. The [conversion milestone](docs/specs/architecture.md#http-response-conversion-verification) records the helper's original checks and limits.

The HTTP handler combines the fixed application origin `http://127.0.0.1:3000` with the original request path and query, and extracts the HTTP method. The Angular adapter constructs a Web Request from these fields and the forwarded headers. The earlier [demonstration module](crates/rubicon/js/render.mjs) remains as a diagnostic example: it displays escaped request fields and a render counter to demonstrate module reuse. It is no longer selected by the executable.

The host converts each request header value into a separate name-value pair, preserving repeated values for the same name. Header names use their normalized form; ordering across different names is unspecified. Values rejected by `HeaderValue::to_str()` produce HTTP 400 before rendering. This provisional text policy does not support every valid HTTP header byte sequence. Earlier demonstration HTTP checks verified repeated values through the worker and JavaScript boundary. The Angular adapter constructs Headers from the pairs, applying Web header normalization.

The HTTP handler generates a decimal request identifier from a process-local atomic counter before header conversion. Client-supplied `X-Request-ID` does not replace it. Identifiers cross the JavaScript boundary as strings, preserving large integer values, and appear in rendering-failure logs. The current Angular adapter accepts the identifier but does not inject it into Angular providers or display it. Identifiers are unique within one server execution, reset on restart, and do not provide authentication or request isolation. Checked increment prevents wrapping: once the counter reaches `u64::MAX`, further matched requests receive HTTP 503. The maximum value itself is not emitted. Library callers supply their own identifier. See the [identifier verification](docs/specs/architecture.md#request-identifier-verification) for checks and limits.

Queue-full and unavailable-worker errors map to HTTP 503; rendering errors map to HTTP 500. The module initialization handshake completes before the HTTP listener is bound, but does not validate the complete renderer contract. Application origin configuration, proxy handling, and API/static-asset routing remain to be implemented.

For HEAD, Angular returns the page representation through the worker and Axum omits its body during HTTP delivery. Repository checks verified status 200, an empty received body, and Content-Length matching the checked GET representation. The complete application response contract remains future work.

The module path currently uses the crate's build-time source directory. Promise-returning exports and continued execution after a rejection are verified with local fixtures, an awaited microtask, and timer callbacks. Angular rendering of the reference pages is now verified through HTTP. Worker configuration, asynchronous native-service and network operations, request isolation, deadline enforcement, graceful shutdown, deployable artifact packaging, and browser hydration through Rust remain future steps. Linker warning LNK4098 persists; performance has not been measured.

The tests verify continued execution after synchronous script errors, rejection of a render when the queue is full, and continued worker execution after export failures or body-conversion errors. Four executable unit tests verify repeated header conversion, rejection of an unsupported text value, identifier uniqueness across four threads, and identifier exhaustion without wrapping. The worker integration check uses [renderer_errors.rs](crates/rubicon/tests/renderer_errors.rs), the controlled [synchronous fixture](crates/rubicon/tests/fixtures/renderer_errors.mjs), an [async wrapper](crates/rubicon/tests/fixtures/renderer_async.mjs), a [timer wrapper](crates/rubicon/tests/fixtures/renderer_timers.mjs), a [streams/abort wrapper](crates/rubicon/tests/fixtures/renderer_streams.mjs), and a [Web objects wrapper](crates/rubicon/tests/fixtures/renderer_fetch_objects.mjs) importing that fixture. Each module runs the same checks in a fresh worker. The wrapper awaits `Promise.resolve()` before calling the imported function, so its intentional exception becomes a rejected Promise. Successful calls return counter values 1, 3, and 5 with request pairs GET/A, HEAD/B, and GET/A across the two failures. Exact comparisons verify status, response-header pairs, and body content containing identifier, URL, and method, including identifiers above JavaScript's safe integer range and query separators and apostrophes in the URLs. Those integration requests currently use empty request-header lists; request-header delivery evidence is recorded in the [architecture](docs/specs/architecture.md#request-header-verification). The async wrapper verifies microtask fulfillment and rejection; the timer wrapper awaits callbacks and checks explicit cancellation; the streams/abort wrapper verifies Unicode pipeline content, closure, and propagation of cancellation. The [async verification](docs/specs/architecture.md#asynchronous-renderer-verification) and [timer verification](docs/specs/architecture.md#web-timers-verification) record those checks and their limits; the [streams/abort milestone](docs/specs/architecture.md#streams-and-abort-verification) records the fourth fixture. The [Web objects milestone](docs/specs/architecture.md#web-request-and-response-verification) records canonical request URLs, header normalization, separate cookies, response cloning, split UTF-8 body decoding, and consumption errors in the fifth fixture.

Run the complete test suite with:

```text
cargo test --locked --manifest-path crates/rubicon/Cargo.toml
```

The sixth integration wrapper, [renderer_performance.mjs](crates/rubicon/tests/fixtures/renderer_performance.mjs), verifies finite clock values, a positive timeOrigin, nondecreasing readings across an awaited timer, named marks with request detail, a nonnegative measure, and removal of its named entries. It retains the same response/error recovery sequence. These are correctness checks with no elapsed-time threshold or benchmark claim.

The integration target has its own `main` (`harness = false`) so it initializes the V8 platform before starting its worker. The test time limits bound asynchronous waits; they do not establish active JavaScript interruption or graceful worker shutdown. A temporary router check verified response metadata delivery, empty HEAD bodies, invalid-response HTTP 500, and subsequent successful requests. That check and its Tower dependency are not retained in the repository. Network checks for the newly connected structured path, load behavior, and request isolation remain separate verification.
